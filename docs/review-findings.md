# ふよみ コードレビュー

レビュー対象は指定された7実装ファイル、`tests/` 全体、`docs/decisions.md`、`SPEC.md`、`CONTRACT.md`。2026-08-23時点の作業ツリーを対象にした。以下の「確認済み」は、コード経路を最後まで追い、可能なものは Node 22.14.0 で実行再現したものだけを指す。

## 結論: 直すべきもの

1. 高 — レベル別の狭い `candidates` により、レベル1の D5 に開放 E5を弾いても正解になる。
2. 高 — 合格・不合格後に新しい発音を待たず、伸ばし続けた同じ音を次の判定へ持ち越す。
3. 高 — マイク初期化失敗時に取得済みストリームが残り、遅れて失敗すると練習開始を二重予約する。
4. 中 — `muteUntil` は判定を止めるが「最初の発音」記録を止めず、おてほん音を本人の発音として記録する。
5. 中 — 第3段のオクターブ救済は現在の条件では到達不能で、仕様・契約・テスト名だけが3段救済を約束している。
6. 中 — 結果画面が未観測の弦・指を主語にし、推奨運指を実演事実のように集計・表示する。
7. 中 — テストは `app.js` の状態機械を一度も動かさず、誤受理を期待値として固定し、オクターブ救済の成功例も検査していない。

重大度「高」は3件で、3件とも Node で再現した。全7件のうち、実行再現は6件、静的確認のみはテスト欠落の1件。

## 1. レベル端の別音を正解にする

**確認済み、Node再現。** 場所は `js/app.js:503-515` と `js/app.js:612-616`、判定側は `js/pitch.js:186-198`。

- 入力: レベル1・イ長調、出題 D5（MIDI 74）に対して、隣の開放弦 E5（MIDI 76）を正確に弾く。
- 結果: `buildCandidates()` はラ線の0〜3だけを渡す。E5が比較候補にないため D5 が「候補中の最近傍」になり、差が +200セントで `RESCUE_MAX_CENTS=250` 内なので `{ok:true}` を返す。音名が明確に異なるのに自動で次へ進む。
- 反証確認: 4弦の候補を与えた同じ判定は `{ok:false, heard:{midi:76,stringId:'E',finger:0}}` になった。したがって検出器の誤差ではなく候補集合の切り方が原因。
- 方針: 出題可能集合と、実音を識別するための競合集合を分ける。少なくとも範囲外の隣接する実在音を最近傍比較へ含め、別音を「端の揺れ」として救済しない。`RESCUE_MAX_CENTS` だけでは2半音の誤受理を防げない。

再現結果:

```text
level-scoped candidates -> { ok: true, cents: 200.00000000000006 }
four-string candidates  -> { ok: false, heard: E-string open E5, cents: 0 }
```

## 2. 持続音が次の問題へ持ち越される

**確認済み、Node再現。** 場所は `js/app.js:596-605`、`js/app.js:678-704`、`js/app.js:707-728` と `js/pitch.js:148-150`。

- 入力: A4を225ms以上伸ばして合格後も弓を止めない。アプリは300ms後に次の音を表示する。
- 結果: `reset()` は保持配列を空にするだけで「いったん無音になったか」を持たない。処理再開後、同じ持続音を新しい発音として225msため直す。次もA4なら触らず自動合格し、次がB4なら前問のA4で誤答・ヒント・再試行が記録される。
- 同じ問題: 不合格後も620msの停止を挟むだけなので、同じ外れ音を伸ばすと約845msごとに再試行回数が増える。
- 方針: 合格後の次問は、信頼できる無音区間または新しいオンセットを観測するまでホールドを再武装しない。不合格後は、同じ安定した外れ音の継続を再度数えず、無音または十分な音高変化から新しい試行を開始する。

再現では、`reset()` の前後で同じA4を与えると両方とも225msで値を返した。2回目を次問B4として判定するとA4の誤答、次問A4ならそのまま正解になった。

## 3. マイク初期化の所有権と後始末が不完全

**確認済み、Node再現。** 場所は `js/pitch.js:61-95` と `js/app.js:421-430`、`js/app.js:445-462`。

- 入力A: `getUserMedia()` がストリームを返した後、`new AudioContext()` が例外を投げる、または `ctx.resume()` が reject する。
- 結果A: `createMic()` は返却オブジェクトを作る前に抜けるため、取得済みトラックを1本も `stop()` せず、作成済みContextも `close()` しない。Nodeスタブでは constructor失敗時 `stoppedTracks:0`、resume失敗時 `stoppedTracks:0, closedContexts:0` を確認した。
- 入力B: `getUserMedia()` が11.2秒の自動フォールバックより遅れて reject し、すでに音を聞かない練習画面へ移っている。
- 結果B: 成功側は `state.screen !== 'check'` を確認するが、`catch` 側には画面確認がない。遅い失敗が `queueManualPractice()` を再度通り、1,600ms後の `beginPractice()` を予約する。実行スタブでは `screen:'practice'` のまま `manualTransitionQueued:true` と1,600msタイマーを確認した。発火すると途中のフレーズが差し替わり、先頭レコードも余分に追加される。
- 方針: ストリーム取得後の全初期化を `try/catch` で所有し、途中失敗時はトラック停止とContext破棄を必ず行う。失敗通知は同じセッションかつ `screen === 'check'` の間だけ有効にし、フォールバック済みの非同期結果を捨てる。

## 4. `muteUntil` 中も最初の発音時刻を記録する

**確認済み、Node再現。** 場所は `js/app.js:596-605`、`js/app.js:916-943` と `js/pitch.js:110-112`、`js/pitch.js:152-156`。

- 入力: おてほん再生中、`muteUntil=2000ms` の状態でスピーカー由来の有声音を `now=1000ms` に検出する。
- 結果: `firstVoiceMs` は `holder.feed()` より先に更新されるため900msになった一方、holderの進捗は0のままだった。結果画面の「最初の発音まで」が本人ではなくアプリのおてほん音を表す。
- 範囲: 判定本体は `muteUntil` で止まっており、この経路での誤合格は確認しなかった。壊れるのは、決定事項が求める事実記録。
- 方針: `playSequence()` が設定した同じミュート期限を発音時刻の採取にも適用する。holderとは別にアプリ側で期限を保持すれば、公開契約を変えずに直せる。

## 5. オクターブ救済が到達不能

**確認済み、Node再現と条件式の証明。** 場所は `js/pitch.js:181-210`。対応仕様は `SPEC.md:50-52` と `CONTRACT.md:59-61`、テストは `tests/pitch.test.mjs:236-277`。

- 入力: 目標A4に対してA3またはA5を入れる。
- 結果: `{ok:false}` で、`oct:true` は返らない。レベル1の全目標を目標差 -2400〜+2400セントで1セント刻みに走査しても、`oct:true` は0件だった。
- 原因: 第3段へ進めるには生の `targetCents` が±250以内である必要がある。その範囲ではオクターブ折り畳み後の目標差も同じ値であり、`cfg.tol` 以内なら第1段ですでにreturn済み、外なら第3段の `<= cfg.tol` を満たせない。実オクターブ差の±1200セントは最初の±250条件で落ちる。
- 方針: ここはコードだけで決めず仕様を一つにする。生の±250を最優先するなら、第3段と「3段救済」の記述を削除する。倍音救済を残すなら、第3段の上限をオクターブ折り畳み後の距離で定義し直し、成功例を契約テストにする。

最も強い反対解釈は「`docs/decisions.md:26` を文字どおり守るならA3/A5の拒否が正しい」である。その場合でも、到達不能コードと `SPEC.md`・`CONTRACT.md` の約束が残る現状は整合していない。

## 6. 結果画面が推奨運指を観測事実として扱う

**確認済み、Node再現。** 場所は `js/app.js:1014-1025`、`js/app.js:1064-1068`。優先決定は `docs/decisions.md:5-11`。

- 入力: 出題レコード `{midi:73,stringId:'A',finger:2,retries:2}` を結果表示する。
- 結果: `ラ線の2（ド♯）で2回やり直した` と表示した。主語が弦・指であり、「このアプリが勧める運指」とも明示していない。また集計キーも `stringId:finger:midi` なので、同じ音高を別の推奨運指で出題すると別項目へ分裂する。
- 方針: 集計は観測・出題できる音高または譜面位置を主キーにする。文言は `ド♯で2回やり直した` を主にし、運指を残すなら `推奨運指: ラ線の2` と明示して従属情報にする。

即時の誤答文 `js/app.js:718-720` は音名が主語で、弦・指が括弧内なので、この決定を守っている。

## 7. 緑のテストが状態機械と救済の意味を守っていない

**確認済み、静的確認。** `node tests/run.mjs` は exit 0 だったが、`tests/run.mjs:9` が拾うテスト群には `app.js` を読み込むものがなく、検索でも参照は0件だった。

- そのため、タイマーの遅延発火、画面遷移、rAF停止、マイク解放、おてほん中の記録、次問への持続音持ち越し、結果文言のどれも回帰検査されない。今回の1〜4と6は全テスト緑のまま再現した。
- `tests/pitch.test.mjs:198-209` は、端候補から+240セントを正解とする期待値で、1の誤受理をむしろ固定している。
- `tests/pitch.test.mjs:236-277` はテスト名に「オクターブの3段」と書くが、オクターブについて確認するのは「1オクターブ下を救済しない」だけで、`oct:true` の成功経路を一度も通さない。
- 方針: `app.js` にDOM・時計・マイクを差し替えられる小さなテスト境界を置き、1〜4と6の再現列を統合テストにする。救済テストは「別音は拒否」と、仕様確定後の「第3段が一度は成功」を直接表す。

常に真になるassertは見つからなかった。問題は、重要な状態遷移を実行していないことと、仕様矛盾を期待値へ写していることにある。
